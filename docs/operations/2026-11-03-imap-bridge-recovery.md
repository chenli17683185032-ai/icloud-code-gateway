## 故障与证据

- 网页健康检查正常，但持久 IMAP 收信进程不存在。
- 旧 watchdog 在 `python -c` 内全文搜索进程命令行中的脚本名；检测代码自身包含该名字，因此无真实收信进程时也返回 `yes`。
- 现场只读复现确认，唯一匹配 PID 就是检测器自身；按完整脚本参数检查则无匹配。
- 现有收信日志最后一次上传为北京时间 2026-10-18 23:59:38，应用容器最近启动为 2026-10-19 01:21:06。

1. 保留原收信代码、密钥、游标、邮件数据、容器及每分钟 cron，不改邮箱配置。
2. 在 GitHub 分支先上传 watchdog 修复、回归测试与本运维记录。
3. 在服务器为旧 watchdog 建立带时间戳备份，仅替换宿主机 watchdog。
4. 以完整的 Python 解释器与脚本参数确认进程；使用 `flock` 避免并发检查重复启动，检测失败不贸然启动。
5. 执行一次 watchdog 启动已有 `/data/run_imap_bridge.py`，不重启 Web、浏览器、代理或其他容器。
6. 检查进程唯一性、收信日志、游标推进、重复 watchdog 幂等性，以及现有公开 API 的鉴权响应。

## 遇到的坑

- 容器 `healthy` 只证明 Web 可用，不能证明外部启动的收信进程存在。
- 命令行子串匹配会匹配 `python -c` 中的源码或 shell 包装命令。
- 修复不能清空游标或盲目重放数据；必须沿用现有断点续收语义。
- 恢复积压同步不等于新邮件端到端验收；需要区分进程运行、历史补收与新邮件实际送达。

## 获得的收获

- watchdog 必须测试“零工作进程但有检测器”的负例，并验证重复执行不会启动多个实例。
- 运维验收需覆盖业务进程及数据进度，不能只依赖 HTTP 200。
- 公共仓库记录操作、风险和验收摘要；生产密钥、原始邮件及敏感证据不进入 Git。
